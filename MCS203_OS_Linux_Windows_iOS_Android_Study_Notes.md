# PART A — LINUX

## A1. Linux architecture — the 10-mark diagram question (Jun23 Q1d, Jun24 Q4b, Dec24 Q2b, Jun26 Q5d)

**One-line definition:** Linux is a **monolithic, Unix-like, multi-user, multitasking OS** in which the entire kernel (process management, memory, file systems, drivers, networking, IPC) runs in a single privileged kernel space, with support for **loadable kernel modules (LKMs)**.

```
┌──────────────────────────────────────────────────────────────┐
│ USER SPACE (unprivileged, ring 3)                            │
│   Applications: shell (bash), editors, web servers, GUI apps  │
│   System libraries: glibc / libc, libpthread, libm             │
└──────────────────────────┬───────────────────────────────────┘
                           │  system calls (int 0x80 / syscall), libc wrappers
┌──────────────────────────▼───────────────────────────────────┐
│ KERNEL SPACE (privileged, ring 0) — MONOLITHIC KERNEL + LKM   │
│  ┌────────────────────┬───────────────────────────────────┐   │
│  │ Process Mgmt       │ Memory Mgmt                       │   │
│  │ fork/exec/wait,    │ VM, paging, demand paging,        │   │
│  │ task_struct, CFS   │ buddy & slab allocators, swap     │   │
│  ├────────────────────┼───────────────────────────────────┤   │
│  │ Virtual File System│ Network Stack                     │   │
│  │ VFS → ext4, xfs,   │ TCP/IP, sockets, netfilter        │   │
│  │ btrfs, procfs, NFS │                                   │   │
│  ├────────────────────┼───────────────────────────────────┤   │
│  │ IPC                │ Device Drivers                    │   │
│  │ pipes, signals,    │ char / block / network drivers    │   │
│  │ msg queues, shm    │ (loadable as modules)             │   │
│  └────────────────────┴───────────────────────────────────┘   │
│  System Call Interface + Loadable Kernel Modules (insmod)     │
└──────────────────────────┬───────────────────────────────────┘
                           │
┌──────────────────────────▼───────────────────────────────────┐
│ HARDWARE: CPU, RAM, disk, NIC, keyboard, display, peripherals │
└──────────────────────────────────────────────────────────────┘
```

**Kernel components you MUST name and explain (one paragraph each):**

1. **Process management** — creates/destroys processes (`fork()`, `exec()`, `wait()`, `exit()`); each process described by a **task_struct** (Process Control Block); states: running, runnable, sleeping, stopped, zombie. Scheduler = **CFS (Completely Fair Scheduler)**, which uses a red-black tree keyed by virtual runtime and gives each task a fair share of CPU.
2. **Memory management** — per-process virtual address space, page tables, demand paging, page-fault handling, allocation via **buddy system** (physical pages in powers of two) and **slab allocator** (small kernel objects), swap and the **OOM killer**.
3. **Virtual File System (VFS)** — an abstraction layer giving one common API (`open`, `read`, `write`, `close`) for many concrete file systems (ext4, XFS, Btrfs, FAT, procfs, NFS). **Everything is a file** in Unix, including devices (`/dev`) and system info (`/proc`).
4. **Network stack** — layered TCP/IP implementation, BSD sockets API, netfilter/iptables for firewalling and NAT.
5. **IPC** — pipes, FIFOs, signals, message queues, semaphores, shared memory, Unix-domain sockets.
6. **Device drivers + LKMs** — code that talks to hardware; can be compiled into the kernel or loaded at runtime with `insmod` / `modprobe` / `rmmod`, which keeps the base kernel small.
7. **System call interface** — the controlled gateway from user space to kernel services; libc wraps these calls.

**⚑ EXTRA (not asked, high-yield if it appears):** boot sequence (BIOS/UEFI → GRUB → kernel decompression → `init`/systemd → runlevels/targets), `systemd`, kernel rings (0 = kernel, 3 = user), monolithic vs microkernel comparison, namespaces + cgroups (the basis of Linux containers/Docker).

## A2. Linux memory management — 10-marker (Jun25 Q3b) + 3 short notes (Dec24 Q5a, Dec25 Q5d, plus diagram)

**Define:** Linux uses **virtual memory with demand paging** — every process gets its own contiguous virtual address space, divided into fixed-size **pages** (typically 4 KB), which are mapped on demand to physical **page frames** via multi-level page tables.

**How it works (steps for the answer):**

1. **Address space layout (32-bit example):** 0–3 GB user space (text, data, BSS, heap ↑, shared libraries, stack ↓), 3–4 GB kernel space. (On 64-bit the split is vastly larger, e.g. 128 TB user.)
2. **Page tables:** virtual address → PGD → PMD → PTE → physical frame + protection bits (present, read/write, user/supervisor, dirty, accessed). Translation is accelerated by the **TLB**.
3. **Demand paging:** a page is loaded from disk only when first touched. A reference to a not-present page raises a **page fault**; the kernel checks the VMA (valid virtual memory area), finds a free frame, reads the page from disk (or fills with zero for anonymous pages), updates the PTE, and restarts the instruction.
4. **Physical allocation:** the **buddy allocator** manages free frames in lists of 2ⁿ contiguous blocks (1, 2, 4 … 1024 pages) — fast, coalesces on free, but suffers internal fragmentation. The **slab allocator** sits on top and carves pages into caches of same-sized objects (e.g. `task_struct`, `inode`) — avoids fragmentation and speeds up allocation.
5. **Zones:** `ZONE_DMA`, `ZONE_NORMAL`, `ZONE_HIGHMEM` (32-bit), because some hardware can only address low memory.
6. **Reclamation:** page replacement uses a modified LRU / active-inactive list; dirty pages are written back by the pdflush/writeback threads. **Swap** moves anonymous pages to a swap partition/file.
7. **Overcommit & OOM killer:** Linux may promise more memory than is physically available; on exhaustion the **Out-Of-Memory killer** selects and kills a process (using a badness score) to free memory.
8. **Page cache:** file-backed pages are cached in RAM; `free`, `vmstat`, `/proc/meminfo` expose the state (buffers/cache vs free vs swap).

**⚑ EXTRA:** `mmap()`, copy-on-write (COW) during `fork()`, huge pages/transparent huge pages (THP), zswap/zram, memory cgroups, KSM (kernel same-page merging), NUMA.

## A3. Linux security — 10-marker (Dec23 Q1d) + 2 short notes (Jun23 Q5c, Jun25 Q5c)

The examiner names the four sub-headings for the 10-mark question. Answer each explicitly:

### (i) User Accounts
- Every user has a unique **UID** and one primary **GID**; groups are in `/etc/group`. **UID 0 = root** (superuser, all privileges).
- `/etc/passwd` — username, UID, GID, home dir, shell (password field is `x`).
- `/etc/shadow` — hashed password, last-change, expiry, lock fields; root-only readable.
- Authentication through **PAM** (Pluggable Authentication Modules); commands `useradd`, `usermod`, `userdel`, `passwd`, `su`, `sudo`.
- Least-privilege principle: use `sudo` instead of logging in as root.

### (ii) File Permissions
- Three classes: **owner (u), group (g), others (o)**; three rights: **read (r=4), write (w=2), execute (x=1)** → 9 bits, e.g. `rwxr-xr--` = 754.
- Directory: `x` = search/traverse, `r` = list, `w` = create/delete entries.
- Commands: `chmod` (change mode, numeric or symbolic), `chown` (owner), `chgrp` (group), `umask` (default mask for new files: usually 022 → files 644, dirs 755).
- **Special bits:** **SUID (4000)** — executable runs with owner's rights (e.g. `passwd`); **SGID (2000)** — runs with group's rights / new files inherit group; **sticky bit (1000)** — only owner can delete in a shared dir (e.g. `/tmp`).
- **ACLs** (`setfacl`/`getfacl`) give per-user/per-group fine-grained rights beyond the three classes.

### (iii) Encrypted Storage
- **LUKS / dm-crypt** — full-disk/partition encryption at the block layer; a passphrase unlocks a master key, data on disk is ciphertext; protects data if the disk is stolen.
- **eCryptfs** / fscrypt — per-file or per-directory encryption (e.g. Ubuntu home-directory encryption, Android FBE).
- Encrypted **swap** and encrypted backups; key management via keyrings / TPM / hardware security module.
- Trade-off: performance overhead, key loss = data loss.

### (iv) Remote Access
- **SSH** (Secure Shell, port 22) — encrypted remote login and command execution; `sshd` daemon; password or public-key authentication (`~/.ssh/authorized_keys`); replace Telnet (cleartext).
- Hardening: disable root login, disable password auth, change port, fail2ban, firewall rules (`iptables`/`nftables`), TCP wrappers, VPN/IPsec for site-to-site access.
- File transfer: `scp`, `sftp`, `rsync` over SSH.

**⚑ EXTRA:** **SELinux / AppArmor** (mandatory access control — a very likely 5-mark extension), capabilities, secure boot, auditing (`auditd`), chroot/jails.

| Dimension | **Linux** | **Windows 10** |

# PART B — WINDOWS 10

## B1. Process management & scheduling — 10-marker (Dec23 Q3b, Dec25 Q1d)

**Define:** A Windows process is an **object** that supplies the resources needed to execute a program — a private virtual address space, an executable image, a table of handles to kernel objects (files, events, semaphores), a security context (access token), and one or more **threads**. The thread, not the process, is the unit of scheduling.

**Key structures (⚑ EXTRA but good depth):** `EPROCESS` (kernel process object), `PEB` (Process Environment Block, user space), `ETHREAD`/`TEB` (thread objects), handle table, access token.

**Process creation sequence:** `CreateProcess()` (kernel32) → `NtCreateUserProcess` (ntdll) → kernel creates `EPROCESS`, address space, initial thread → loader maps EXE and DLLs → entry point runs.

**Process states:** ready → running → waiting/blocked → terminated (plus suspended states).

**Scheduling:** Windows uses **preemptive, priority-driven, round-robin with multilevel feedback queues**.
- **32 priority levels (0–31).** Levels 0–15 = variable (normal user processes); 16–31 = real-time (fixed).
- Each thread has a **base priority** (from priority class: idle, low, below normal, normal, above normal, high, real-time) plus **dynamic boosts** (e.g. foreground window, I/O completion, GUI interaction) that decay over time — this is the *feedback* element.
- Each thread gets a **time quantum**; when it expires the thread is preempted and put at the back of its priority queue. Foreground processes get longer quanta and boosts for responsiveness.
- SMP support: threads can migrate across processors; **processor affinity** can pin them; scheduler is NUMA-aware (⚑ EXTRA).

**Thread vs process (relates to Dec25 Q5b short note):** a process is a resource container; a thread is a schedulable execution path sharing the process's address space and handles, with its own stack, registers and TLS. Threads are cheaper to create/switch; communication is via shared memory; a crash in one thread can kill the process.

**⚑ EXTRA:** fibers (user-mode scheduled threads), job objects (group management of processes), I/O completion ports, Windows service architecture, DLLs and the Win32 API.

## B2. Windows memory management — 10-marker (Jun24 Q1d)

Asked in two named halves — answer both.

### (i) Virtual Memory Organization
- Each process sees a **large, private, contiguous virtual address space**, independent of physical RAM. On 32-bit: 2 GB user + 2 GB kernel (or 3 GB user with the `/3GB` switch); on 64-bit: up to ~128 TB user.
- The virtual space is divided into **regions**: free, reserved, committed. `VirtualAlloc()` reserves/commits; `VirtualFree()` releases.
- Layout (32-bit): 0–64 KB NULL region, user code/data, heap, loaded DLLs, stack, then kernel space. **ASLR** randomises the layout (⚑ EXTRA).
- The **memory manager** maintains **page tables** mapping virtual pages → physical frames or a copy on the **pagefile** (`PAGEFILE.SYS`). **PAE** (Physical Address Extension) lets 32-bit Windows use >4 GB RAM (⚑ EXTRA).
- Benefits: process isolation (one process cannot touch another's memory), more address space than RAM, memory-mapped files, copy-on-write sharing of DLLs and EXE images.

### (ii) Demand Paging
- Pages are brought into RAM **only when referenced**. On a reference to a non-resident page the MMU raises a **page fault**; the memory manager checks if the address is valid, finds a free frame (or evicts one), reads the page from the pagefile or mapped file, updates the PTE, and restarts the faulting instruction.
- **Working set** = the set of pages currently resident for a process; the *working-set manager* trims it under memory pressure (aging).
- **Soft fault** = page is still in physical memory but not in this process's PTE (e.g. after sharing); **hard fault** = requires disk I/O — expensive.
- Page replacement is **FIFO-like with working-set trimming** plus a modified-page writer; clock-style algorithms are used internally (⚑ EXTRA).
- **DEP** (Data Execution Prevention) marks pages non-executable; **memory compression** (Win 10) compresses pages instead of immediately writing to disk (⚑ EXTRA).

**Diagram to draw:** virtual address → page table → (present? → physical frame in RAM | not present → page fault handler → pagefile on disk → frame) → TLB on the side.

## B3. IPC in Windows — 5-marker (Dec24 Q2a)

**Define:** IPC is the mechanism by which two processes exchange data or synchronise. Windows offers:

| Mechanism | Description |
|:---|:---|
| **Named / anonymous pipes** | Byte-stream or message-oriented; named pipes work over a network and support client–server (from CreateNamedPipe) |
| **Mailslots** | One-way, datagram-style broadcast messaging (good for small messages, e.g. "I am here" announcements) |
| **Memory-mapped files (file mapping)** | A file (or the pagefile) mapped into the virtual address space of several processes → fastest way to share large data; each process sees the same physical pages |
| **COM (Component Object Model)** | Binary interface standard for reusable software components; supports local and remote (DCOM) calls, reference counting |
| **RPC (Remote Procedure Call)** | Call a procedure in another process/computer as if local; Microsoft RPC uses ALPC locally |
| **ALPC / LPC** | Advanced Local Procedure Call — fast, private kernel IPC used by system services |
| **Sockets / Winsock** | TCP/IP network communication between processes on different machines |
| **Windows messages / WM_COPYDATA** | GUI applications send messages; WM_COPYDATA passes a small block of data |
| **Clipboard, DDE** | User-driven data exchange (clipboard), legacy Dynamic Data Exchange |
| **Synchronisation objects** | Mutex, semaphore, event, critical section, waitable timer — coordinate shared access (synchronisation rather than data transfer) |

**Answer structure:** define IPC → say Windows supports both *shared-memory* and *message-passing* styles → name 4–5 mechanisms with one line each → note that everything is exposed as kernel **objects accessed through handles** with security descriptors.

## B4. File system management in Windows — 5-mark note (Jun23 Q5b)

- **NTFS** is the standard Windows file system. Features to list: **MFT (Master File Table)** — every file/directory is a record in a database-like table; support for large volumes and 64-bit addresses; **journaling** via `$LogFile` for crash recovery; **ACL-based security** per file/folder; **EFS** (Encrypting File System) and **BitLocker** volume encryption; NTFS **compression**; disk **quotas**; **hard links**, **symbolic links/junctions**, **alternate data streams**; **USN change journal**.
- Other file systems: FAT32/exFAT (removable media, broad compatibility), ReFS (resilient, for servers/storage spaces).
- Directory structure: hierarchical, drive-letter roots (`C:\`), folders, paths, attributes (hidden, system, read-only, archive).
- **File allocation methods** (ties to Jun26 Q3b): **contiguous** (fast sequential/direct access, fragmentation) vs **non-contiguous** — linked allocation (FAT: file allocation table of next-block pointers; no external fragmentation, slow direct access) and indexed allocation (NTFS uses **extents**/run lists and index structures; fast direct access).

**⚑ EXTRA:** Windows registry, VSS (Volume Shadow Copy), OneDrive/Storage Sense, DFS, BitLocker recovery keys.

## C2. iOS layered architecture — THE diagram question (Jun24 Q1c, Jun25 Q1d, Dec25 Q4b)


## C3. iOS directories & iCloud container — 5-mark note (Jun23 Q5e, Dec24 Q5d)

Every app lives in a **sandbox** with a container directory. The standard sub-directories:

| Directory | Purpose | Backed up? |
|:---|:---|:---|
| **Documents/** | User-generated content, documents the app creates; can be exposed via file sharing | **Yes** — iCloud/iTunes backup |
| **Library/Preferences/** | `NSUserDefaults` / preference plists | Yes |
| **Library/Caches/** | Cache files that can be recreated; app must handle eviction | **No** |
| **Library/Application Support/** | App-created support data, not user documents | Yes |
| **tmp/** | Temporary scratch files; OS purges when app is not running | **No** |
| **<AppName>.app** (bundle) | The signed, **read-only** app bundle — executable + resources | Part of the app itself |

- `NSHomeDirectory()` gives the app's container; use `NSSearchPathForDirectoriesInDomains` / `FileManager.urls(for:in:)` to locate directories rather than hard-coding paths.
- **iCloud container** — a special ubiquity container `iCloud.<teamID>.<bundleID>` for data synced across the user's devices via **iCloud Drive**. Access via `FileManager.url(forUbiquityContainerIdentifier:)`; coordinate file access with `NSFileCoordinator`; track changes with `NSFilePresenter`/`NSMetadataQuery`.
- **CloudKit** — structured public/private database in iCloud; **iCloud key-value store** — small settings; **iCloud backup** — device backup including app data.
- Data protection: files are encrypted with classes tied to device lock state (e.g. "complete until first user authentication").

**⚑ EXTRA:** App Groups (shared container between related apps), App Extensions containers, Documents/Inbox for opened-in files, iCloud Drive vs. ubiquity.

## D2. Android memory management — 10-marker (Dec23 Q4b) + 5-mark note (Jun23 Q5d)

**Define:** Android is based on Linux, so it uses **virtual memory, paging and per-process address spaces**, but it adds a mobile-specific policy: **it does not rely on traditional swap**. Instead it aggressively kills low-priority processes to reclaim memory, using the **Low Memory Killer (lmkd)** with an `oom_adj` score derived from the process importance hierarchy.

**Points to cover:**

1. **Per-process heap** — each app runs in its own process with its own virtual address space; the heap is managed by the **ART garbage collector** (mark-sweep; generational; large object space) — apps do not free memory explicitly.
2. **Categories of memory in a process** (importance hierarchy, linked to Q3 below): **foreground → visible → service → background → empty/cached**. The lower the importance, the higher the kill priority.
3. **Low Memory Killer (LMK / lmkd)** — monitors free memory against thresholds; when below a threshold it kills processes with the highest `oom_adj` (background/empty first) to free pages. This keeps the foreground app responsive.
4. **No swap; zRAM + KSM** — instead of disk swap, Android compresses anonymous pages in RAM (**zRAM**, compressed swap device) and de-duplicates identical pages (**KSM**). This avoids slow flash I/O and preserves flash life. (⚑ EXTRA but high-scoring.)
5. **Process lifecycle callbacks** — as memory gets tight the system calls `onLowMemory()` / `onTrimMemory(level)` so apps can release caches before being killed.
6. **Memory accounting** — PSS (Proportional Set Size, shared pages counted proportionally) is the meaningful metric, not RSS; `dumpsys meminfo`.
7. **Share memory** — Android shares framework code and resources across processes (e.g. via `mmap` of the `.art` image and Zygote fork COW) to reduce total footprint.

**Link to the 5 process types (Jun25 Q3a):** the LMK uses exactly this hierarchy to decide whom to kill.

## D3. The five Android process types — 10-marker (Jun25 Q3a)

Answer with the **importance order (highest → lowest)** and state *when killed*:

| # | Type | When a process is in this state | Kill priority |
|:--:|:---|:---|:---|
| 1 | **Foreground** | Hosts an Activity the user is interacting with (onResume), or a Service bound to it, or a BroadcastReceiver executing `onReceive()`, or a foreground service with a notification | **Killed only as a last resort** |
| 2 | **Visible** | Activity is paused but still visible to the user (e.g. behind a transparent/dialog-themed activity), or a service bound to a visible activity | Very low — killed only if no foreground processes can be freed |
| 3 | **Service** | Hosts a started Service that is not tied to UI (background music playback, file sync, download) | Low-ish — killed only if needed for foreground/visible processes |
| 4 | **Background** | Activity has been stopped (covered by another app, user pressed Home); not visible and no running service | **High** — kept in an LRU list and killed first when memory is needed |
| 5 | **Empty** | No active application components at all; retained only in the cache to speed up the next launch of that app | **Killed first** / no reason to keep it |

**Add one line:** Android ranks processes by this hierarchy and the **LMK kills from the bottom up**; the goal is to keep the user-visible experience smooth. Also mention `onTrimMemory()` callbacks give a chance to survive.

## D4. File management & security in Android — 10-marker (Jun24 Q2a)

### File management
- Linux-based file system: partitions **/system** (read-only OS, ART, framework), **/vendor** (HAL, vendor drivers), **/data** (user apps and data), **/cache**, **/boot**, **/recovery**, **/sdcard** (emulated external storage). File systems: **ext4**, **F2FS** (flash-friendly), and on newer devices **EROFS** for /system.
- Each app gets a private data directory **`/data/data/<package-name>/`** (mode 0700) with subdirs `files/`, `cache/`, `databases/` (SQLite), `shared_prefs/` (XML preferences), `databases/`. Only that app's UID can read it.
- External storage: app-specific external dirs and public shared storage (MediaStore); scoped storage (⚑ EXTRA, Android 10+).
- Data exchange: **Content Providers** with URI permissions, Intents, and (historically) world-readable external storage.

### Security
1. **Application sandbox** — each app is assigned a **unique Linux UID** and runs in its own process; it cannot read another app's files or memory.
2. **Permissions model** — permissions declared in `AndroidManifest.xml` (`<uses-permission>`); installation-time on old versions, **runtime permissions** on Android 6.0+ (Marshmallow) for **dangerous** permissions; protection levels: **normal, dangerous, signature, signatureOrSystem**. User grants/revokes at runtime.
3. **SELinux** — mandatory access control enforced since Android 5.0 (Lollipop), in **enforcing** mode; confines even privileged processes. This is a major difference from older Linux desktop setups.
4. **Application signing** — every APK must be signed with a developer certificate; verifies integrity and enables permission inheritance / updates.
5. **Verified Boot + dm-verity** — checks the OS image at boot; tampered images are detected.
6. **Keystore / KeyChain** — cryptographic keys stored in a hardware-backed keystore (TEE/StrongBox); keys are non-exportable.
7. **Device encryption** — full-disk encryption (FDE) and modern **file-based encryption (FBE)** with **Direct Boot**; screen lock, secure unlock.
8. **Network security** — TLS by default, Network Security Configuration, cleartext traffic restrictions, Certificate Transparency (⚑ EXTRA).
9. **Intent and component controls** — exported components, permission guards, `android:permission`, URI permissions.

**⚑ EXTRA:** Android's four application components (Activity, Service, BroadcastReceiver, ContentProvider), the **Intent** mechanism (explicit/implicit, filters), AndroidManifest structure, the `adb` tool, Play Protect, sandbox escape history.
